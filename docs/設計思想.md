## Reactを採用している理由

### 1. エンタープライズでの採用実績

Reactは2025年時点で、大規模組織の68%がフロントエンド開発に採用しています。

採用の決め手:

1. 人材の豊富さ: 最大規模の開発者プール
2. エコシステムの安定性: 長期サポートと後方互換性
3. 段階的な導入: 既存システムへの漸進的な統合が可能
4. 長期サポート: Meta（旧Facebook）による継続的なメンテナンス

出典:

- [State of React 2025: Key Takeaways for Developers](https://strapi.io/blog/state-of-react-2025-key-takeaways)
- [What is React.js in 2025](https://merge.rocks/blog/what-is-react-js-in-2025-and-why-react-19-changed-front-end-again)

### 2. React 19の新機能による恩恵

プロジェクトはReact 19を採用しており、以下の恩恵を受けています：

| 機能               | 恩恵                                          |
| ------------------ | --------------------------------------------- |
| Actions            | フォーム送信の簡素化（loader/actionパターン） |
| useOptimistic      | 楽観的更新によるUX向上                        |
| use() hook         | 非同期データの宣言的な取り扱い                |
| Compiler（実験的） | 自動的なメモ化による再レンダリング最適化      |

出典:

- [What's new in React 19 - Vercel](https://vercel.com/blog/whats-new-in-react-19)
- [React 19 Features & Updates (2025)](https://weqtechnologies.com/react-19-features-updates-2025-whats-new-why-it-matters/)

### 3. Server Componentsを採用しない理由

React 19ではServer Components（RSC）が正式リリースされましたが、プロジェクトでは採用していません。

採用しない理由:

1. Context API非互換: RSCではContext APIが使用できない（最大の障壁）
2. テストの複雑さ: RSC用のテスト環境がまだ成熟していない
3. 既存ライブラリとの互換性: 多くのReactライブラリがRSC未対応
4. 学習コスト: チーム全体のキャッチアップが必要

代わりに採用したアプローチ:

- React Router v7のloader/actionパターンでサーバーサイド処理を実現
- SSRによる初期表示の高速化
- バンドルサイズはコード分割で最適化

出典:

- [React Server Components: Adoption Challenges and Solutions for 2025](https://vladimirsiedykh.com/blog/react-server-components-adoption-challenges-2025)
- [React Server Components in Production: Benefits, Pitfalls and Best Practices](https://www.growin.com/blog/react-server-components/)

> "RSC adoption faces Context API limitations, testing gaps, bundler complexity, and compatibility issues with existing React libraries." - Vladimir Siedykh

## React Router v7を採用した理由（Next.jsとの比較）

### 1. フレームワーク選定の背景

プロジェクトはReact Router v7のFramework Modeを採用しています。これはRemixの機能がReact Routerに統合されたもので、フルスタックフレームワークとして機能します。

### 2. React Router v7 vs Next.js 比較表

| 観点           | React Router v7                         | Next.js                     |
| -------------- | --------------------------------------- | --------------------------- |
| 設計思想       | Web標準・プログレッシブエンハンスメント | RSCファースト・Vercel最適化 |
| SSRアプローチ  | loader/action + streaming               | RSC + App Router            |
| データフェッチ | loader関数（サーバー専用）              | Server Components内で直接   |
| フォーム処理   | Web標準Form + action                    | Server Actions              |
| デプロイ先     | 任意のNode.js環境                       | Vercel最適化（他も可能）    |
| バンドラー     | Vite                                    | Turbopack（Webpack後継）    |
| 学習曲線       | React Router経験者に低い                | RSC理解が必要               |
| 型安全性       | 自動生成された型（.react-router/）      | 手動定義が多い              |

出典:

- [Comparison | TanStack Start vs Next.js vs React Router](https://tanstack.com/start/latest/docs/framework/react/comparison)
- [React Router vs Next.js Router: Key Differences](https://medium.com/@mwandanam/react-router-vs-next-js-router-key-differences-and-when-to-use-them-b4c3d1fb3f10)

### 3. React Router v7を選んだ理由

#### 3.1 Web標準への準拠

```typescript
// React Router v7: Web標準のFormData、fetch、Headersを使用
export const action = async ({ request }: ActionFunctionArgs) => {
  const formData = await request.formData(); // Web標準API
  const name = formData.get("name");
  // ...
};
```

> "React Router's philosophy is 'Web fundamentals with progressive enhancement' - it embraces web platform primitives (fetch, FormData, Headers) and works without JavaScript by default." - TanStack Comparison

#### 3.2 プログレッシブエンハンスメント

JavaScriptが無効でもフォームが動作します：

```tsx
// JavaScriptなしでもPOST送信が可能
<Form method="post">
  <input name="email" type="email" />
  <button type="submit">送信</button>
</Form>
```

#### 3.3 Remixからの移行コスト

プロジェクトの前身がRemixベースであったため、React Router v7への移行が最も低コストでした。

#### 3.4 デプロイ先の柔軟性

Vercelに依存せず、Google Cloud Run等の任意の環境にデプロイ可能：

```
プロジェクトのデプロイ先: Google Cloud Run (asia-northeast1)
├── apps/app → https://app.プロジェクト.jp
└── apps/inspection → https://inspection.プロジェクト.jp
```

### 4. Next.jsを採用しなかった理由

#### 4.1 Vercel依存への懸念

> "Next.js's philosophy is 'Production-ready with optimal defaults, best with Vercel' - featuring RSC-first deep integration with React Server Components, Vercel-optimized infrastructure." - TanStack Comparison

プロジェクトはGoogle Cloud Platform（Cloud Run）でホスティングしており、Vercel最適化の恩恵を受けられません。

#### 4.2 RSCの成熟度

2025年時点でも、RSCは以下の課題を抱えています：

- Context API非互換（59件の報告で最大の障壁）
- テストギャップ（24件の報告）
- 既存ライブラリとの互換性問題

出典:

- [State of React 2025](https://strapi.io/blog/state-of-react-2025-key-takeaways)

#### 4.3 パフォーマンス特性

React Router v7は特定のユースケースでNext.jsより高いスループットを達成できます：

> "In controlled server-side rendering tests using identical React applications, Next.js achieved around 51 requests per second while @fastify/react hit 271 requests per second." - Better Stack

ただし、Next.js 16ではTurbopackにより大幅なパフォーマンス改善が行われています。

出典:

- [Next.js vs. Fastify + React: A Performance and DX Comparison](https://betterstack.com/community/comparisons/nextjs-vs-fastify-react/)
- [React SSR Benchmark: TanStack, React Router, Next.js](https://blog.platformatic.dev/react-ssr-framework-benchmark-tanstack-start-react-router-nextjs)

### 5. Next.jsの方が適しているケース

以下の場合はNext.jsを検討すべきです：

1. Vercelでホスティングする場合: 最適化されたインフラの恩恵
2. RSCを積極活用したい場合: 最も成熟したRSCサポート
3. 画像最適化が重要な場合: next/imageの高度な最適化
4. ISR（Incremental Static Regeneration）が必要な場合: Next.js固有の機能
5. 新規プロジェクトでReact経験が浅い場合: 豊富なドキュメントとコミュニティ

## SSR/CSRの設計戦略

### 1. SSRファーストの設計原則

プロジェクトはSSRをデフォルトで有効にしています：

```typescript
// apps/app/react-router.config.ts
export default {
  ssr: true, // SSRがデフォルト
  future: {
    v8_middleware: true, // middleware機能を有効化
  },
} satisfies Config;
```

### 2. データフェッチ戦略

#### 2.1 loaderパターン（サーバーサイド）

```typescript
// routes/structures/loader.server.ts
export async function loader({
  request,
}: LoaderFunctionArgs): Promise<LoaderData> {
  // 1. 認証チェック（サーバーサイドで実行）
  const authenticatedUser = await requireAuth(request);

  // 2. データ取得（Firestoreへの直接アクセス）
  const repositories = getRepositories();
  const structures = await repositories.structure.findByProject(
    tenantId,
    projectId,
  );

  // 3. N+1クエリ回避のための並列取得
  const inspectionPromises = structures.map((structure) =>
    repositories.inspection.findByStructure(tenantId, projectId, structure.id),
  );
  const inspectionArrays = await Promise.all(inspectionPromises);

  return { structures, inspections };
}
```

ポイント:

- `.server.ts`拡張子でサーバー専用コードを明示
- Firestoreへのアクセスはloaderのみ（クライアントにAdmin SDKを含めない）
- `Promise.all`でN+1クエリを回避

#### 2.2 actionパターン（データ変更）

```typescript
// routes/settings/action.server.ts
export const action = async ({ request }: ActionFunctionArgs) => {
  const formData = await request.formData();
  const intent = formData.get("intent");

  switch (intent) {
    case "UPDATE_SETTINGS":
      // Zod検証
      const submission = parseWithZod(formData, { schema: settingsSchema });
      if (submission.status !== "success") {
        return submission.reply(); // バリデーションエラーを返す
      }
      // Firestore更新
      await repositories.settings.update(submission.value);
      return redirect("/settings");
  }
};
```

### 3. Middleware連鎖パターン

プロジェクトの最も特徴的な設計はmiddleware連鎖です：

```
Request
  ↓
require-auth middleware（認証チェック）
  ├→ 失敗: ログインへリダイレクト
  └→ 成功: context.set(userContext, user) → next()
      ↓
structure-layout middleware（構造物検索）
  ├→ 見つからない: 全案件を横断検索 → 自動切り替え
  └→ 成功: context.set(structureContext, structure) → next()
      ↓
loader（データ取得）
  └→ context.get(structureContext) でmiddlewareのデータを取得
      ↓
Component（UI表示）
```

具体的な実装例:

```typescript
// layouts/structure-layout/server/middleware.ts
const structureMiddleware: Route.MiddlewareFunction = async (
  { request, params, context },
  next,
) => {
  const { structureId } = params;

  // 現在の案件で構造物を検索
  let structure = await repositories.structure.findById(
    tenantId,
    projectId,
    structureId,
  );

  if (structure) {
    // 見つかった場合、contextに設定して次へ
    context.set(projectStructureContext, { structure, projectId, tenantId });
    return await next();
  }

  // 見つからない場合、全案件を横断検索
  for (const project of projects) {
    structure = await repositories.structure.findById(
      tenantId,
      project.id,
      structureId,
    );
    if (structure) {
      // 別の案件で見つかった → 自動で案件切り替え
      throw redirect(request.url, {
        headers: [
          ["Set-Cookie", await setSelectedProjectId(request, project.id)],
        ],
      });
    }
  }

  throw new Response("Structure not found", { status: 404 });
};
```

### 4. クライアントサイドの状態管理

原則: サーバー状態はloader、UI状態のみuseState

```tsx
// routes/structures/route.tsx
export default function Structures() {
  // サーバーから取得したデータ（loader経由）
  const { structures } = useLoaderData<typeof loader>();

  // UIの一時的な状態のみuseState
  const [page, setPage] = useState(1);
  const [isDialogOpen, setIsDialogOpen] = useState(false);

  // 派生データはuseMemoで計算
  const paginated = useMemo(
    () => structures.slice((page - 1) * PAGE_SIZE, page * PAGE_SIZE),
    [structures, page],
  );

  return (
    <Table>
      {paginated.map((item) => (
        <Row key={item.id} {...item} />
      ))}
    </Table>
  );
}
```

### 5. useEffectを避ける設計

悪い例（useEffectでデータフェッチ）:

```tsx
// ❌ 避けるべきパターン
function BadComponent() {
  const [data, setData] = useState(null);

  useEffect(() => {
    fetch("/api/data")
      .then((res) => res.json())
      .then(setData);
  }, []);

  return data ? <View data={data} /> : <Loading />;
}
```

良い例（loaderでデータフェッチ）:

```tsx
// ✅ 推奨パターン
export async function loader() {
  const data = await repositories.getData();
  return { data };
}

export default function GoodComponent() {
  const { data } = useLoaderData<typeof loader>();
  return <View data={data} />; // ローディング状態不要
}
```

### 6. CSRが必要なケース

以下の場合のみクライアントサイドで処理します：

| ケース                           | 実装方法                        |
| -------------------------------- | ------------------------------- |
| ダイアログの開閉                 | `useState`                      |
| ページネーション                 | `useState` + `useMemo`          |

| Canvas/SVG描画                   | `useRef` + `useEffect`          |
| ジェスチャー操作                 | `useEffect`（イベントリスナー） |

## TypeScript型定義戦略

### 1. 型定義の階層構造

プロジェクトでは型定義を明確に階層化しています：

```
packages/domains/src/
├── damage-details/
│   ├── damage-detail.ts       # 型定義（TypeScript）
│   ├── damage-detail.schema.ts # Zodスキーマ
│   └── index.ts               # エクスポート
```

### 2. 型定義ファイル（.ts）

```typescript
// packages/domains/src/damage-details/damage-detail.ts

// 1. 定数定義（as const で型安全に）
export const DAMAGE_TYPE = {
  CURRENT: "CURRENT",
  PREVIOUS: "PREVIOUS",
} as const;

// 2. 定数から型を導出
export type DamageType = (typeof DAMAGE_TYPE)[keyof typeof DAMAGE_TYPE];
// → 'CURRENT' | 'PREVIOUS'

// 3. エンティティ型定義
export type DamageDetail = {
  id: string;
  locationId: string;
  groupId: string;
  type: DamageType;
  category: string;
  pattern: string;
  severity: string;
  classification: string;
  note: string;
  createdAt: Date;
  updatedAt: Date;
};

// 4. 集約型
export type DamageDetailPair = {
  groupId: string;
  current: DamageDetail | null;
  previous: DamageDetail | null;
};
```

### 3. Zodスキーマファイル（.schema.ts）

```typescript
// packages/domains/src/damage-details/damage-detail.schema.ts
import { z } from "zod";
import type { DamageDetail } from "./damage-detail";
import { DAMAGE_TYPE } from "./damage-detail";

// 1. 完全スキーマ（satisfiesで型との整合性を保証）
export const damageDetailSchema = z.object({
  id: z.string().min(1),
  locationId: z.string().min(1),
  groupId: z.string().min(1),
  type: z.enum(Object.values(DAMAGE_TYPE) as [string, ...string[]]),
  category: z.string(),
  pattern: z.string(),
  severity: z.string(),
  classification: z.string(),
  note: z.string(),
  createdAt: z.date(),
  updatedAt: z.date(),
}) satisfies z.ZodType<DamageDetail>;
// ↑ satisfies演算子で型の整合性をコンパイル時に検証

// 2. Firestore保存用（自動生成フィールドを除外）
export const damageDetailDocumentSchema = damageDetailSchema.omit({
  id: true,
  locationId: true,
});

// 3. 作成用（timestampsなし）
export const createDamageDetailSchema = damageDetailSchema.omit({
  id: true,
  locationId: true,
  createdAt: true,
  updatedAt: true,
});

// 4. 更新用（partialでオプショナルに）
export const updateDamageDetailSchema = createDamageDetailSchema.partial();
```

### 4. satisfies演算子の重要性

`satisfies z.ZodType<T>`により、以下を保証します：

1. 型とスキーマの同期: 型定義を変更するとスキーマもエラーになる
2. コンパイル時検証: ランタイムエラーを事前に防止
3. IDEサポート: 自動補完と型チェックが効く

```typescript
// 型を変更した場合
export type DamageDetail = {
  id: string;
  newField: string; // 新しいフィールドを追加
  // ...
};

// Zodスキーマでエラーが発生（satisfiesのおかげ）
export const damageDetailSchema = z.object({
  id: z.string(),
  // newFieldがないのでエラー！
}) satisfies z.ZodType<DamageDetail>;
// ❌ Type 'ZodObject<...>' does not satisfy the expected type 'ZodType<DamageDetail>'
```

### 8. Repositoryでの型検証フロー

```typescript
// packages/repositories/src/domain/projects/project.repository.ts
export class ProjectRepository extends BaseRepository<Project> {
  async create(tenantId: string, data: CreateProjectInput): Promise<Project> {
    // 1. 入力データをZodで検証
    const validatedInput = createProjectSchema.parse(data);

    // 2. Firestoreに保存
    const docRef = await this.adapter.add(path, validatedInput);

    // 3. 取得したデータをZodで検証して返す
    const doc = await docRef.get();
    return projectSchema.parse({ id: docRef.id, tenantId, ...doc.data() });
  }

  async findById(tenantId: string, projectId: string): Promise<Project | null> {
    const doc = await this.adapter.get(path);
    if (!doc.exists) return null;

    // Firestoreから取得したデータを必ずZodで検証
    return projectSchema.parse({ id: doc.id, tenantId, ...doc.data() });
  }
}
```

検証フロー図:

```
外部入力（フォーム、API）
  ↓
Zod検証（createSchema）
  ↓
Firestore保存
  ↓
Firestore取得
  ↓
Zod検証（fullSchema）
  ↓
型安全なオブジェクト → アプリケーション
```

## 適しているプロジェクト

### 1. 中規模〜大規模の業務アプリケーション

理由:

1. モノレポ構成により、複数のアプリケーション間でコードを共有できる
2. TypeScript Project Referencesで依存関係を明確に管理できる
3. Repository層の抽象化により、ビジネスロジックとデータアクセスを分離できる

具体例:

- 社内業務システム（CRM、ERP、在庫管理）
- B2B SaaSプラットフォーム
- 複数テナント対応のマルチアプリケーション

出典:

## 適していないプロジェクト

### 1. 大規模リアルタイムアプリケーション

理由:

1. Firestoreには10,000 writes/秒の制限がある
2. 同時接続数に上限がある（Realtime Database: 200,000接続）
3. 複雑なリアルタイムクエリのパフォーマンスが低下する可能性

具体例:

- 大規模チャットアプリケーション（Slack、Discord規模）
- リアルタイム協調編集（Google Docs規模）
- 高頻度のストリーミングデータ処理

出典:

- [Usage and limits | Firestore | Firebase](https://firebase.google.com/docs/firestore/quotas)
- [Scaling Firebase - Practical considerations and limitations](https://ably.com/topic/scaling-firebase-realtime-database)

> "There is a 10,000 writes per second limit to the entire Cloud Firestore database. For 1,000,000 concurrent users with 100,000 active users, that 10,000/s limit can be very restrictive." - Ably

---

### 2. 複雑なクエリが必要なアプリケーション

理由:

1. FirestoreはOR条件やNOT条件の複合クエリをネイティブサポートしない
2. 集計クエリ（GROUP BY、SUM、AVG）が限定的
3. JOINに相当する操作はクライアント側で実装が必要

具体例:

- 複雑なレポート生成システム
- データ分析ダッシュボード
- 全文検索が主要機能のアプリケーション

出典:

- [Firestore Query & Record Limitations: How To Work Around It](https://estuary.dev/blog/firestore-limitations/)

> "Firestore does not natively support OR queries on multiple fields or NOT queries." - Estuary

代替案:

- PostgreSQL + Prisma
- Supabase
- Algolia（全文検索）との併用

---

### 3. 完全に独立したマイクロサービス

理由:

1. モノレポは共有コードがあるプロジェクトで最も効果を発揮
2. 独立したサービス間で共有がない場合、オーバーヘッドが大きい
3. チーム間のコード分離が厳密に必要な場合は不向き

具体例:

- 異なる技術スタックのマイクロサービス群
- 完全に独立した外部委託プロジェクト
- 厳密なアクセス制御が必要なセキュリティ要件

出典:

- [When to Use a MonoRepo: Benefits, Drawbacks, and Best Practices](https://medium.com/debugging-diaries/when-to-use-a-monorepo-benefits-drawbacks-and-best-practices-51d88770ee7b)
- [Monorepo vs. multi-repo | Thoughtworks](https://www.thoughtworks.com/en-us/insights/blog/agile-engineering-practices/monorepo-vs-multirepo)

> "If your projects are totally independent, or if you need strict access controls (where some teams shouldn't see specific code), then polyrepos may be your go-to choice." - Medium

---

### 4. ベンダーロックインを避けたいプロジェクト

理由:

1. FirebaseはGoogleエコシステムに依存
2. 移行コストが高い（データ構造、認証、ストレージ）
3. 価格体系の変更リスク

具体例:

- 長期的なコスト予測が重要なエンタープライズ
- マルチクラウド戦略を採用するプロジェクト
- オンプレミス要件があるプロジェクト

出典:

- [Understanding Firebase Costs and Integration Challenges](https://www.metacto.com/blogs/the-true-cost-of-firebase-setup-integration-and-maintenance-in-2024-complete-breakdown)
- [Firebase limitations](https://www.cometchat.com/blog/firebase-limitations)

> "Using Firebase ties your application to Google's ecosystem. Migrating away from Firebase can be challenging if your application grows beyond its capabilities." - CometChat

代替案:

- Supabase（PostgreSQL、オープンソース）
- 自前のバックエンド（Node.js + PostgreSQL）

---

### 5. 小規模な単一ページアプリケーション

理由:

1. モノレポのオーバーヘッドが利点を上回る
2. ビルド設定の複雑さが不要
3. SSRが不要な場合、React Router v7のdeclarativeモードで十分

具体例:

- シンプルなランディングページ
- 単機能のツール（計算機、コンバーター）
- プロトタイプ・デモアプリ

出典:

- [Benefits and challenges of monorepo development practices - CircleCI](https://circleci.com/blog/monorepo-dev-practices/)

> "A monorepo is worth it when projects share code/config, are versioned/released together, or need synchronized changes. If services are independent with minimal sharing, polyrepo may be simpler." - CircleCI

代替案:

- Vite + React（SPA）
- React Router v7のdeclarativeモード
- Astro（静的サイト）

---

### 6. 超大規模リポジトリ（1000万行以上）

理由:

1. Gitのパフォーマンスが低下する
2. IDE・エディタの動作が遅くなる
3. CI/CDパイプラインが複雑化

具体例:

- Google・Facebook規模のコードベース
- 100人以上の開発者が同時に作業するプロジェクト
- 長い歴史を持つレガシーシステムの統合

出典:

- [Monorepo Explained](https://monorepo.tools/)

> "Monorepos are difficult to scale up. Commands like git blame may take unreasonably long times, IDEs begin to lag and productivity suffers." - monorepo.tools

代替案:

- Bazel / Buck / Pants（専用ビルドシステム）
- Turborepo / Nx（高度なモノレポツール）
- 戦略的なリポジトリ分割

## 判断フローチャート

```
プロジェクト要件を確認
    │
    ├─ 複数アプリ間でコード共有が必要？
    │   ├─ Yes → モノレポテンプレート適合 ✓
    │   └─ No → 単一リポジトリを検討
    │
    ├─ SEO/初期表示速度が重要？
    │   ├─ Yes → SSR対応テンプレート適合 ✓
    │   └─ No → SPA構成を検討
    │
    ├─ 外部データのバリデーションが多い？
    │   ├─ Yes → Zod統合テンプレート適合 ✓
    │   └─ No → TypeScriptのみで可
    │
    ├─ 10,000 writes/秒を超える？
    │   ├─ Yes → Firestore以外を検討 ✗
    │   └─ No → テンプレート適合 ✓
    │
    ├─ 複雑なSQL的クエリが必要？
    │   ├─ Yes → RDB（PostgreSQL等）を検討 ✗
    │   └─ No → テンプレート適合 ✓
    │
    ├─ Vercelでホスティング予定？
    │   ├─ Yes → Next.jsも検討
    │   └─ No → React Router v7が適合 ✓
    │
    └─ ベンダーロックインを許容できる？
        ├─ Yes → テンプレート適合 ✓
        └─ No → オープンソース代替を検討 ✗
```

---

## まとめ

### このテンプレートが最適なケース

| 特性             | 説明                              |
| ---------------- | --------------------------------- |
| プロジェクト規模 | 中規模〜大規模（5〜50人のチーム） |
| アプリ構成       | 複数アプリでコード共有あり        |
| データ要件       | CRUD中心、複雑なクエリ不要        |
| トラフィック     | 中程度（〜10,000 writes/秒）      |
| SEO要件          | 重要（SSR/SSG活用）               |
| 開発速度         | 高速なプロトタイピングから本番へ  |
| デプロイ先       | Vercel以外（Cloud Run等）         |

### このテンプレートを避けるべきケース

| 特性             | 説明                          |
| ---------------- | ----------------------------- |
| プロジェクト規模 | 超小規模 or 超大規模          |
| アプリ構成       | 完全に独立したサービス        |
| データ要件       | 複雑なクエリ、集計、全文検索  |
| トラフィック     | 超高頻度のリアルタイム更新    |
| インフラ要件     | ベンダーロックイン回避必須    |
| チーム構成       | 厳密なコードアクセス制御必要  |
| デプロイ先       | Vercel（Next.jsの方が最適化） |
